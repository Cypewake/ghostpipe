# ghostpipe 开发文档 —— 实现讲解

> 配套 [设计文档.md](设计文档.md)（协议定稿）阅读。本文讲"代码怎么写的、为什么这么写、踩了什么坑"。
> 所有行号引用以 git 仓库提交版本为准。语言 Go 1.26，**零第三方依赖**（仅标准库）。

---

## 1. 工程结构

```
ghostpipe/
├── cmd/
│   ├── server/main.go     # 服务端 CLI：-listen -psk -mode -ws -insecure-tls
│   ├── client/main.go     # 客户端 CLI：-server -psk -fingerprint -tunnel -socks5 -mode -ws
│   └── filesrv/main.go    # 测试靶标：小文件 HTTP 服务（verify-all 用）
├── internal/
│   ├── protocol/          # 帧编解码 + 信令 Payload + 错误码（自底向上的第一层）
│   ├── auth/              # 双向 HMAC 质询应答
│   ├── transport/         # 传输层：Conn 帧级封装 / TLS / SPKI / WebSocket 载体
│   ├── stream/            # Stream 接口 + ConnStream + Pump
│   ├── mux/               # 多路复用 + 双层信用流控（并发最复杂的一层）
│   ├── socks5/            # SOCKS5 入口（注入拨号回调，与协议层解耦）
│   ├── server/            # 会话 / 隧道注册 / 端口归属表 / 心跳
│   └── client/            # 重连循环 / M1 数据连接 / SOCKS5 出口
├── docs/                  # 设计文档 + 本文档
├── assets/logo.png
└── verify-all.sh          # 一键端到端回归（6 场景 11 断言）
```

**分层依赖单向向下**：`cmd → server/client → mux/socks5/stream → auth/transport → protocol`。
无环、无跨越层级的引用——每层可以独立单测（mux 测试用 `net.Pipe` 模拟双端，不需要真网络）。

**零第三方依赖的理由**：① WebSocket 载体手写 RFC 6455 子集（~200 行）即可满足"binary 帧 + 握手 + 关闭"最小面；② TLS 用标准库 `crypto/tls` + `InsecureSkipVerify` + 自行比对 SPKI（`tls.ConnectionState().PeerCertificates[0].RawSubjectPublicKeyInfo` 的 SHA-256）实现 pinning，比引入根证书校验更贴合自签场景；③ 作品集价值：面试官可以直接审全部代码，不存在"这坨是库"的黑盒。

## 2. protocol —— 帧编解码

### 2.1 帧头与"先校验后分配"

`frame.go` 的 `ReadFrame` 是整个工具的安全根基：

```go
n := binary.BigEndian.Uint32(h[9:13])
if n > MaxPayload {                       // 16KB 上限
    return nil, fmt.Errorf("%w: Length=%d 超过上限", ErrProtoViolation, n)
}
buf := make([]byte, n)                    // 校验通过才分配
```

恶意方发 `Length=0xFFFFFFFF` 不会预分配 4GB——直接以 `proto-violation` 断连。
`ErrProtoViolation` 用 sentinel error（`errors.Is` 可判），上层据此区分"网络断了"和"对方违反协议"（后者要立即断连且不再重试同一连接）。

`WriteFrame` 拒绝写出超限 Payload（发送侧同样受约束，而不是只防别人）。

### 2.2 Payload 编解码器

每个信令一个 `EncodeXxx/DecodeXxx` 对（`EncodeRegister`/`EncodeOpenM1`/`EncodeCredit`/`EncodeError`/`EncodeU16`）。
规则统一：**u16 长度前缀字符串**（先写 2 字节长度再写内容），大端整数。
好处：帧格式变更只动这一层；单测覆盖每个编解码器的 roundtrip。

## 3. auth —— 双向 HMAC

时序（设计 §4.1，**server 永远先说话**）：

```
S→C  AUTH_REQ{nonce_s}                # 16B CSPRNG
C→S  AUTH_RESP{nonce_c, hmac_c}       # HMAC-SHA256(PSK, "c"‖nonce_c‖nonce_s)
S→C  AUTH_OK{hmac_s}                  # HMAC-SHA256(PSK, "s"‖nonce_c‖nonce_s)
```

**为什么 server 先发**（实现偏差 #2）：最初设计是"client 先发首帧 + server peek 分诊"，但 M1 数据连接也会被 client 拨入，两端在"谁先出第一帧"上互等 → 死锁。定稿：`handleConn` 里 `auth.ServerChallenge(c)` 无条件先发 challenge，然后读首帧分诊（`AUTH_RESP`→控制会话 / `DATA_BIND`→M1 数据连接 / 其他→违规断连）。**服务端先发让"连接角色"由 client 的应答帧自描述**，一个入口处理两种连接。

client 侧 `auth.Client` 不仅应答，还**校验服务端的 `hmac_s`**——PSK 双向证明，防恶意 server / 中间人（设计第 1 轮 #3 修正：单向认证不可接受）。

测试覆盖：成功握手、错 PSK 双侧失败、握手超时（10s）、坏应答拒绝。

## 4. transport —— 分层包装与载体

### 4.1 分层顺序（对称性铁律）

```
client: TCP → [WebSocket] → [TLS]          server: TCP → [WebSocket] → [TLS]
```

**踩坑实录**：最初 server 端写成 TLS→WS，client 是 WS→TLS，S4 场景（WS+TLS）报 "HTTP request to an HTTPS server"。教训：**分层顺序是协议的一部分，两端必须逐层对称**。修正后 server `Listen` 与 client `Dial` 都按 TCP→WS→TLS 顺序堆叠。

### 4.2 Conn：帧级连接封装

`transport.Conn` 在 `net.Conn` 之上提供：
- `Send/Receive` 帧级读写，**一把互斥锁串行化写方向**（多 goroutine 并发 `Send` 不交错）；
- `LastRecv() atomic` 最近入帧时间戳——心跳判死统一用它（"任何入帧都证明链路活着"，比逐次 PONG 计数少一个状态机，实现偏差 #5）；
- `Done()` 连接死亡广播 channel（心跳循环 select 等它）。

### 4.3 SPKI 指纹 pinning

`GenerateSelfSigned`（ECDSA P-256 自签）→ server 启动打印 `SHA256(SPKI)`；
client `Dial` 强制：`-fingerprint` 未配置且 TLS 开启 → 拒绝拨号（CLI 层就拦）。
TLS 握手后取 `PeerCertificates[0].RawSubjectPublicKeyInfo` 算 SHA-256 与配置比对，不符即断。
**无静默降级**：TLS 失败不会回退明文；要明文必须两端同时显式 `-insecure-tls`。

### 4.4 WebSocket 载体（ws.go，零依赖 RFC 6455 子集）

只实现需要的面：binary 帧、client 掩码 / server 不掩码、握手（SHA1 accept-key）、关闭帧、ping/pong。
难点是 `SetDeadline`——WebSocket 没有 TCP 级 deadline，实现用 **watchdog 定时器**：每次读写重置定时器，到期关闭底层连接，让阻塞中的读写以错误返回。诚实超时而非假接口。

## 5. stream —— 抽象层（M1/M2 共用的关键）

```go
type Stream interface {
    Read(p []byte) (int, error)
    Write(p []byte) (int, error)
    Close() error
}
```

- `ConnStream`：M1 的实现，直接包一个真 TCP 连接。
- `MuxStream`：M2 的实现（mux 包）。
- `Pump(a, b io.ReadWriteCloser)`：双向转发器，两个对向 copy goroutine，一端 EOF/错误即双向关闭。

**上层转发逻辑只认 `Stream` 接口**——server 的 `acceptExternal`、client 的本地拨号转发在 M1/M2 间零改动切换，这是设计第 1 轮 #14（M1→M2 重写问题）的落地。

---

## 6. mux —— 多路复用（最复杂的一层）

### 6.1 真死锁实录与单写者队列（最重要的实现决策）

**现象**：20 流并发测试在 125s 超时。两端的读循环都在"处理帧 A 时同步 `Send` 应答帧 B"，`net.Pipe` 是同步语义（写阻塞到对端读），于是：我方读循环等对方读应答 → 对方读循环等我方读它的应答 → 系统级死锁。

**修复**：所有出帧经 `sendCh`（深度 4096）队列，**唯一 `sender()` goroutine** 串行写出：

| 路径 | 函数 | 语义 |
|---|---|---|
| 应用路径（用户数据/开流） | `sendAsync` | 入队 + 阻塞等结果；连接死亡立即返回 `ErrConnClosed` |
| 读循环路径（CREDIT/PONG 应答） | `trySend` | **非阻塞**入队，队列满则丢弃（自愈：后续帧会再触发） |

原则：**读循环内绝不阻塞**。控制连接的心跳、信用补充都走 `trySend`，读循环永远只做分发。

### 6.2 双层信用流控

| 层 | 窗口 | 归还时机 | 目的 |
|---|---|---|---|
| 连接级 | 1MB | 帧读入内存**即回**（`handleData` 里无条件 `trySend(CREDIT, 0, n)`，迟到帧也回） | 保护 socket 读缓冲；流关闭不泄漏连接级窗口 |
| 流级 | 256KB/流 | 本地应用 `Read` 消费后回（端到端背压） | 慢消费者不拖死整条连接 |

写方 `Stream.Write` 分片 = `min(16KB, 流信用, 连接信用)`；信用不足 `cond.Wait()`——**控制帧不受窗口约束**，CREDIT 必然能到达，等待必然被唤醒（第二轮 #3 死锁修正）。

防御性检查：对端违反窗口（流缓冲 > 2×窗口）→ `proto-violation` 断连。互信但不傻信。

### 6.3 StreamID 与迟到帧

- client 奇数 / server 偶数，从 1/2 起步，每次 +2，**永不复用**（`closedIDs` 集合保留到连接结束）；
- 已关闭流上的 DATA/CREDIT：静默丢弃 + `lateFrames` 计数（不断连——in-flight CLOSE 竞态下误杀正常流）；
- DATA 指向**未知**流（既非活跃也非已关闭）：`proto-violation` 断连（真违规）。
- 触顶 2^31 → `id-exhausted` ERROR + 连接级 teardown。

### 6.4 读循环分发与回调异步化

`dispatch` 里对 `onControl`（REGISTER 等）、`onOpenTunnel`、`onOpenAddr` 一律 `go h(...)` 异步执行——回调里做 `net.Dial` 可能秒级阻塞，绝不能卡读循环。**"先注册流再交回调"**（`handleOpen`）保证回调启动后的 DATA 一定路由得到。

## 7. server —— 会话与隧道管理

### 7.1 连接分诊（handleConn）

```
Accept → 先发 AUTH_REQ → 读首帧
  ├─ AUTH_RESP → 双向认证 → 控制会话（mux 读循环 或 M1 读循环 + 心跳）
  ├─ DATA_BIND → M1 数据连接：原子消费 token → 与等待的外部连接 Pump 对接
  └─ 其他      → proto-violation 断连
```

### 7.2 全局端口归属表（实现偏差 #3，设计文档没有的新结构）

```go
ports map[uint16]*session   // Server 级，portMu 保护
```

场景：client 被 `kill -9`，server 的读循环立刻感知 TCP 断开并 `teardown`（释放端口）——此时旧会话已死，新 client 重连注册无冲突。**但如果旧会话是半开状态**（NAT 重置/网线拔插，server 侧 TCP 未断），心跳 15s 才判死，而新 client 退避 1-2s 就重连了——新 REGISTER 到来时旧会话还活着，仅靠"会话内替换"管不到别的会话占的端口。

解决：REGISTER 处理时先查全局表——
- 表里是别的会话 → `prev.dropTunnel(port)`：从旧会话摘除隧道、关旧 listener、清旧 pending，**强制接管**；
- 表里是自己/无 → 走常规同会话替换或新建。

`teardown` 与 `registerTunnel` 都对表做"检查归属再删除"（`if s.ports[port] == sess`），避免误删新会话的注册。

### 7.3 M1 token 生命周期

`pendings map[[32]byte]*pendingBind`（≤64），每条带 `time.AfterFunc(10s)` 过期回收。
清理时机全覆盖：过期 / DATA_BIND 消费 / 同会话重注册 / 跨会话接管 / 会话断连（`clearPendingBySession`）。
client 本地拨号失败时，通过 `ERROR{remote-refused, "rr:"+token hex}` 告知 server 回收等待中的外部连接（**happy path 之外的失败也走信令**，不靠 10s 超时兜底）。

### 7.4 心跳

`heartbeatLoop`：5s tick → `LastRecv` 超 15s 断连 teardown；否则发 PING。
挂双条件：`conn.Done()` 触发也 teardown——读循环死亡（对端 RST）不等心跳立即收敛。

### 7.5 服务端 SOCKS5 入口（实现偏差 #7，用户质疑驱动补齐）

frp 的 socks5 插件方向：外部用户连 VPS 代理端口 → 流量穿透到**客户端内网**出网 → 可访问内网任意设备。
v1 初版只有客户端本地 SOCKS5（反向：内网借道 VPS 出网），缺这个方向——只有固定端口转发能到内网设备。补齐：

- `Server` 增加 `cur *session`（curMu 保护，v1 单客户端）：`handleConn` 认证成功后 `setCur`，`teardown` 时 `clearCur`；
- `Run` 里按 `-socks5` 启动 `socks5.Serve(ln, s.socksDial)`，`socksDial(target)` = 取 cur 会话 → `sess.mux.OpenAddr(target)` → **服务端发 OPEN_ADDR(S→C)** → 客户端 `handleOpenAddr` 在内网 `net.Dial(target)` → Pump 对接；
- 客户端在线判断：cur == nil 或 mux == nil（conn 模式）→ 报"无客户端在线"，SOCKS5 回 general failure；
- mux 层**零协议改动**：`handleOpen` 本来就不校验 StreamID 奇偶方向，OPEN_ADDR 双向化只动了两端的回调注册。

`socks5.Serve` 的 dial 回调注入设计在这里第二次复用——同一个包，client 侧注入"经 VPS 出网"、server 侧注入"经客户端内网出网"。

## 8. client —— 重连循环

### 8.1 退避重连（loop）

```
失败 → wait = backoff + rand(backoff/4)   # 抖动防惊群
      backoff = min(backoff*2, 60s)
曾建立过会话 → 重连成功后 backoff 重置 1s
```

`stopped` 原子标志 + `stopCh` 双保险，`Shutdown()` 时正在 sleep 的退避立即打断退出。

### 8.2 M1 数据连接上的"迟到挑战"（实现偏差 #2 的推论）

server 对**所有**入连接先发 AUTH_REQ（包括数据连接）。client 的数据连接不发 AUTH_RESP、直接发 `DATA_BIND{token}`——之后必须**吞掉一条迟到的 AUTH_REQ**再开始 Pump，否则 challenge 字节会污染转发流（S2 场景 "400 Bad Request" 的根因）。代码里注释明确标注这是"连接角色自描述的实现细节"。

### 8.3 失败路径全部走信令

`handleOpenM1` 五个失败分支（隧道不存在/本地拒绝/数据连接失败/绑定写失败/挑战异常）统一 `fail()` → 按 token 发 `ERROR{remote-refused}` 让 server 回收外部连接。

### 8.4 SOCKS5（M4，双向）

`socks5.Serve(ln, dialCallback)`——SOCKS5 状态机（无认证 + CONNECT）与隧道零耦合，拨号经回调注入。两个方向两个入口：

| 入口 | 位置 | dial 回调 | 数据出网侧 |
|---|---|---|---|
| 客户端 `-socks5` | 内网机器本地 | `cl.openAddr` → `mux.OpenAddr`（C→S） | 服务端（VPS）出网 |
| 服务端 `-socks5` | VPS 上 | `srv.socksDial` → `sess.mux.OpenAddr`（S→C） | **客户端内网**拨号（frp socks5 插件等价） |

client 的 `handleOpenAddr`（服务端下发目标的接收端）：内网 `net.DialTimeout(8s)`，失败发 `ERROR{remote-refused}` 并关流。
client `New` 里强校验：本地 SOCKS5 只能配 mux 模式；server 同样校验其 SOCKS5 只能配 mux。

### 9.2 端到端回归（verify-all.sh，6 场景 11 断言）

| 场景 | 内容 |
|---|---|
| S1 | mux 模式：TCP 隧道 + HTTP 文件拉取校验内容一致 |
| S2 | conn 模式：独立数据连接 + DATA_BIND 绑定 |
| S3 | SOCKS5：动态出口 curl 校验 |
| S4 | WebSocket 载体（+TLS） |
| S5 | kill -9 客户端 → 退避重连 → 第二次注册成功、端口恢复服务 |
| S6 | 错误 PSK → 认证拒绝（负路径） |

**工程细节**：
- **日志语义探针**替代网络轮询：`wait_log "$log" "控制端口已监听"` / `"隧道就绪"`——不猜服务何时可用，直接等"完成动作"的日志行（网络轮询在 TLS 端口上浪费 20s 的教训）；
- 环境隔离：`unset http_proxy https_proxy …` + `NO_PROXY='*'`——本机系统代理会把 curl 的回环请求路由到代理（S1 第一次失败的根因）；
- 端口全用高位随机，脚本可重复执行（防覆盖）。

## 10. 踩坑实录汇总（面试可讲）

| # | 坑 | 根因 | 修法 |
|---|---|---|---|
| 1 | mux 20 流并发死锁 | 读循环内同步 Send + net.Pipe 同步语义 → 双端互等 | 单写者队列（sendAsync/trySend 双路径） |
| 2 | 认证互等死锁 | client 等挑战 / server peek 首帧，谁都不先动 | server 永远先发 AUTH_REQ；首帧自描述连接角色 |
| 3 | M1 转发流污染（400） | 数据连接上迟到的 AUTH_REQ 混入转发字节 | client 绑定后吞掉一条挑战帧再 Pump |
| 4 | S4 "HTTP to HTTPS server" | 两端 TLS/WS 分层顺序不对称 | 统一 TCP→WS→TLS 逐层对称 |
| 5 | curl 走了系统代理 | 本机 `http_proxy` 环境变量劫持回环请求 | 脚本内 unset + NO_PROXY='*' |
| 6 | TLS 端口网络轮询浪费 20s | 轮询语义 ≠ 服务就绪语义 | 日志语义探针 wait_log |
| 7 | kill -9 后重连端口冲突 | 半开会话心跳未判死，端口未释放 | 全局端口归属表 + 跨会话强制接管 |
| 8 | SOCKS5 语义方向与用户预期不符（发布后质疑发现） | v1 只实现了"客户端本地入口→VPS 出网"，而"经代理访问客户端内网"（frp socks5 插件方向）缺失 | OPEN_ADDR 双向化 + 服务端 `-socks5` 入口（偏差 #7）；**教训：交付前用用户视角过一遍用法语义，而不只是跑通自测场景** |
| 9 | 手写 roundup 偏差（教训来自外部） | CVSS 取整规则误解——写数值类代码必须对官方规范逐条核对 | —（方法论警示） |

## 11. 已知限制（v1 明示不做）

- 无半关闭（CLOSE 即双向关）——SSH/HTTP 场景无影响；
- 无 UDP / STCP / 多 client 共享 / 流量看板（不对标 frp 全集）；
- 单 client 单会话（多隧道走同一会话）；
- 认证失败无速率限制（依赖部署层防火墙/.fail2ban）；
- Windows 下 `kill -9` 场景的端口接管依赖 server 侧 TCP 感知，极端半开仍需等 15s 心跳。

## 12. 后续方向（v2 候选）

- `instance_id` 参与替换策略（当前仅日志观测）；
- 服务端管理端口（隧道列表/流量统计）；
- fuzz 深化：go-fuzz 常驻 + 语料库沉淀。
